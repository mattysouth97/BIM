# Phase 43: IFC4 Round-Trip Export — Research

**Researched:** 2026-04-12
**Domain:** IFC4 STEP export via web-ifc WASM, property set authoring, Worker architecture
**Confidence:** HIGH (web-ifc write API verified directly from installed package; IFC4 standard verified from buildingSMART; encoding verified from ISO-10303-21 spec)

---

## Summary

Phase 43 requires writing IFC4 STEP files from the app's semantic instance model (built in Phase 35-36) using the `web-ifc` WASM already installed in the project at `^0.0.77`. The write API is **fully present** in the installed version: `CreateModel`, `WriteLine`, `WriteLines`, `SaveModel`, `CreateIfcEntity`, `CreateIfcType`, and `DeleteLine` are all exported from `web-ifc-api.d.ts` and confirmed in the compiled JS. No additional library is needed for the core write path.

The architecture is: an in-app Web Worker loads the `web-ifc` WASM (the `web-ifc-mt.wasm` multi-thread build is already present), receives a serialized element graph from the main thread, builds the IFC4 entity graph entity-by-entity using `WriteLine`, then calls `SaveModel` to get a `Uint8Array` which is transferred back to the main thread via `postMessage` with a `Transferable`.

Korean characters in IFC strings require `\X2\...\X0\` escape encoding (ISO 10303-21 Part 1 rule) — raw UTF-8 Korean bytes are not valid in STEP strings unless the file declares `ISO-10303-21;` edition 3 support, which most validators and authoring tools do not yet handle. Use the `\X2\` code page escape for all non-ASCII characters.

**Primary recommendation:** Use `web-ifc@0.0.77` write API directly. Do not hand-roll a STEP writer. Structure the export as a Worker with chunked batch `WriteLines` calls and `postMessage` progress events.

### 1.1 API Availability

**Confirmed in `node_modules/web-ifc/web-ifc-api.d.ts`:** [VERIFIED: local package]

### 1.2 Minimal Write Pattern

[VERIFIED: from issue #462 ThatOpen/engine_web-ifc, confirmed against type declarations]

```typescript
// In a Web Worker — do not import this on the main thread
import * as WebIFC from "web-ifc";

const api = new WebIFC.IfcAPI();
await api.Init((path) => path.endsWith(".wasm") ? "/wasm/" + path : path);

// 1. Create empty IFC4 model
const modelID = api.CreateModel({
  schema: "IFC4",
  name: "BIM Export",
  description: ["Generated by Korea BIM Digital Twin"],
  authors: [],
  organizations: ["GX Team"],
});

// 2. Write entities using typed class constructors
//    IFC4 namespace: WebIFC.IFC4.IfcXxx
//    IFC2X3 namespace: WebIFC.IFC2X3.IfcXxx
const dir = new WebIFC.IFC4.IfcDirection(
  /* expressID */ 1000,
  [new WebIFC.IFC4.IfcReal(1), new WebIFC.IFC4.IfcReal(0), new WebIFC.IFC4.IfcReal(0)]
);
api.WriteLine(modelID, dir);

// 3. Serialize to bytes
const data: Uint8Array = api.SaveModel(modelID);

// 4. Always close model to free WASM heap
api.CloseModel(modelID);

// 5. Transfer bytes to main thread
self.postMessage({ type: "done", data }, [data.buffer]);
```

### 1.3 Alternative: IfcOpenShell.js

If web-ifc write proves insufficient for complex geometry (unlikely given confirmed API), the alternative is IfcOpenShell compiled to WASM via Emscripten. [ASSUMED] IfcOpenShell has a Python-first API; its WASM/JS bindings are experimental and not production-ready as of 2025. The web-ifc path is strongly preferred for this project.

### 1.4 Custom STEP Writer

Writing raw ISO 10303-21 STEP text is possible as a pure-JS fallback but requires implementing the full STEP grammar, EXPRESS schema ordering, and IFC4 validation rules. This is a significant engineering effort (estimated 2-3 weeks) with no testing tooling. Use only as last resort if web-ifc write is blocked by a critical bug.

### 3.3 How to Use `revit-property-map.ts` as Shared Read+Write Dictionary

The existing `REVIT_PROPERTY_SETS` record in `src/lib/ifc/revit-property-map.ts` maps `Pset_name → [{ ifcKey, target }]`. This is currently read-only (import → extraction). For write, **extend with a reverse mapping function**:

```typescript
// Proposed extension to revit-property-map.ts
export function buildPropertySet(
  psetName: string,
  values: Partial<ExtractedMaterial>
): Record<string, unknown> {
  const mappings = REVIT_PROPERTY_SETS[psetName] ?? [];
  const result: Record<string, unknown> = {};
  for (const m of mappings) {
    if (m.target === "uValue" && values.uValue !== undefined)
      result[m.ifcKey] = values.uValue;
    if (m.target === "thermalConductivity" && values.thermalConductivity !== undefined)
      result[m.ifcKey] = values.thermalConductivity;
  }
  return result;
}
```

This keeps the read and write dictionaries in sync — a single source of truth. The writer reads property names from the same `REVIT_PROPERTY_SETS` map that the importer uses.

| Custom Pset Name (proposed) | Property | Type | Notes |

| `KR_GreenBuilding_Energy` | `BuildingEnergyGrade` | `IfcLabel` | e.g., `"1++"` |

## 4. Worker Architecture

### 4.1 Design

```
Main Thread                         Export Worker
─────────────────────────────       ────────────────────────────────────
ifc-export-worker.ts                ifc-writer-worker.ts
  new Worker("ifc-writer")   ──→   onmessage({ type: "export", payload })
  onmessage progress updates  ←──  postMessage({ type: "progress", pct })
  onmessage done              ←──  postMessage({ type: "done", data: Uint8Array },
                                               [data.buffer])  // transferable
```

**Why off-thread:** `api.Init()` loads and compiles the WASM module (50-200ms). `SaveModel` serializes a potentially large byte buffer. `WriteLines` for 100k instances may take several seconds. All of this must not block the renderer.

**Worker file location:** `src/workers/ifc-writer-worker.ts`

The project's existing `ifc-loader.tsx` uses the same pattern — dynamic `import("web-ifc")` on demand with a custom `locateFile` handler pointing to `/wasm/`. Replicate this in the worker.

### 4.2 Progress Reporting

Use a chunked write loop with `postMessage` progress events between chunks:

```typescript
// In worker
const CHUNK_SIZE = 1000; // entities per chunk
const chunks = chunkArray(allEntities, CHUNK_SIZE);

for (let i = 0; i < chunks.length; i++) {
  api.WriteLines(modelID, chunks[i]);
  self.postMessage({ type: "progress", pct: Math.round((i / chunks.length) * 90) });
  // yield to allow message queue to flush (macrotask)
  await new Promise(r => setTimeout(r, 0));
}

const data = api.SaveModel(modelID); // last 10% of progress
self.postMessage({ type: "progress", pct: 100 });
self.postMessage({ type: "done", data }, [data.buffer]);
```

### 4.3 Memory Budget for 100k Instances

[ASSUMED: based on web-ifc WASM heap characteristics and general STEP serialization patterns]

| Model Size | Estimated WASM Heap | Estimated Output File | Notes |
|------------|--------------------|-----------------------|-------|
| 10k instances | ~50 MB | ~5 MB .ifc | Comfortable |
| 50k instances | ~200 MB | ~25 MB .ifc | Within browser limits |
| 100k instances | ~400 MB | ~50 MB .ifc | At limit of some mobile browsers |

**Mitigations for large models:**
- Use `SaveModelToCallback` instead of `SaveModel` to stream output in chunks rather than allocating one large `Uint8Array`
- Write elements in waves (Level 1 → Level 2 → ...) rather than loading full instance graph at once
- For very large models (>100k), offer a "levels to export" selection in the UI
- Always call `api.CloseModel(modelID)` immediately after `SaveModel` to free WASM heap

**WASM multi-threading:** The package ships `web-ifc-mt.wasm` (multi-threaded build). It can be activated by passing `{MEMORY: sharedArrayBuffer}` in `LoaderSettings`. However, in a Dedicated Worker, `SharedArrayBuffer` requires `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp` headers — verify these are set in `next.config.ts` before enabling MT mode. For Phase 43, **start with single-threaded** and enable MT only if < 60s target is not met.

## 5. Round-Trip Test Strategy

### 5.1 Export → Re-import → Diff Pattern

```typescript
// Test outline (Jest / Vitest)
describe("IFC4 round-trip", () => {
  it("preserves geometry within 1% tolerance", async () => {
    const model = buildTestModel(); // 1 wall, 1 slab, 1 window
    const exported: Uint8Array = await exportToIFC4(model);
    const reimported = await importFromIFC4(exported);

    expect(reimported.wallArea).toBeCloseTo(model.wallArea, 1); // 1% = 1 decimal
    expect(reimported.floorAreas[0].area).toBeCloseTo(model.floorAreas[0].area, 1);
  });

  it("preserves U-values exactly", async () => {
    const uValue = 0.35; // W/m²K
    const model = buildTestModelWithUValue(uValue);
    const exported = await exportToIFC4(model);
    const reimported = await importFromIFC4(exported);
    expect(reimported.materials[0].uValue).toBe(uValue); // exact, not approximate
  });
});
```

**Geometry tolerance:** The app stores dimensions as floating-point meters. IFC4 STEP serializes reals with 6+ decimal places. Re-import via the existing `extractGeometry` function. A 1% tolerance on area sums is achievable; per-vertex position tolerance requires geometry streaming which is not in the current import path.

**U-value exact preservation:** `IfcThermalTransmittanceMeasure` is a REAL in STEP, serialized as the JS `number` itself. No precision loss occurs unless the value is transformed (e.g., W/m²K → BTU conversion and back). Keep values in SI throughout.

## 6. Risks and Mitigations

### Risk 1: web-ifc write is incomplete for complex geometry

**Probability:** LOW — write API is confirmed present and functional for standard entities.
**Trigger:** Complex swept solids, IfcBooleanClippingResult (openings in walls), or IfcFacetedBRep fail to serialize correctly.
**Mitigation:** Phase 43 scope uses `IfcExtrudedAreaSolid` only (no openings in Phase 43). Use `IfcBoundingBox` for MEP. Wall openings (doors/windows as voids) can be deferred to Phase 43+. Track GitHub issues on ThatOpen/engine_web-ifc for geometry write bugs.

Known issue: IFC2X3 `IfcDirection` write was broken (issue #462). IFC4 write was confirmed working in the same issue. **Stay on IFC4 schema.**

### Risk 2: Large file performance (>100k instances, >60s target)

**Probability:** MEDIUM for full building corpus.
**Mitigation:**
- Use `WriteLines` (batch) rather than `WriteLine` in a loop — single WASM FFI call per chunk
- Use `SaveModelToCallback` to avoid 50MB single allocation
- Offer UI-level scope filter (export selected levels/disciplines)
- Enable WASM MT mode if single-thread exceeds budget (requires COOP/COEP headers)
- As benchmark: web-ifc processes ~1M entities/sec on desktop. 100k instances with ~10 entities each = ~1M total entities = ~1s entity creation + serialization overhead.

### Risk 3: Korean character encoding in IFC strings

**Probability:** HIGH if raw UTF-8 Korean is written directly to IfcText values.
**Root cause:** ISO 10303-21 Part 1 (used by virtually all IFC tools) only allows ISO 8859-1 printable chars directly. Korean characters (가-힣, U+AC00–U+D7A3) are outside this range.
**Mitigation:** Implement a `encodeIfcString(str: string): string` utility that:
1. Detects non-ASCII characters
2. Encodes them as `\X2\` + UTF-16BE hex codes + `\X0\`
3. Example: `"콘크리트"` → `\X2\CE58D06AC8B4B9AC\X0\`

This encoding is required for:
- Element names (e.g., `"외벽 콘크리트 200mm"`)
- Property set values where Korean text is stored
- Organization names in `IfcOwnerHistory`

web-ifc's `IfcText` type accepts a plain JS string — the library does NOT automatically apply `\X2\` encoding. [ASSUMED: based on STEP standard and web-ifc string handling behavior — verify by writing a test Korean string and inspecting the output bytes]

### Risk 4: WASM memory leak from unclosed models

**Probability:** HIGH if `CloseModel` is not called.
**Mitigation:** Use try/finally in the worker:
```typescript
let modelID: number | null = null;
try {
  modelID = api.CreateModel({...});
  // ... write entities ...
  const data = api.SaveModel(modelID);
  return data;
} finally {
  if (modelID !== null) api.CloseModel(modelID);
}
```

### Risk 5: IfcGloballyUniqueId collisions on re-export

**Probability:** MEDIUM if GUIDs are regenerated on each export.
**Mitigation:** Generate GUIDs once per element (in Phase 30 element registry) and store as a stable property. On export, read the stored GUID rather than calling `CreateIFCGloballyUniqueId` each time. This also enables diff-based re-import (same GUID = same element, update rather than replace).

### 7.2 Korean String Encoding Utility

```typescript
// src/lib/ifc/ifc-string-encoder.ts
export function encodeIfcString(str: string): string {
  let result = "";
  let hasNonAscii = false;
  for (const char of str) {
    const code = char.codePointAt(0)!;
    if (code > 126 || code < 32) {
      if (!hasNonAscii) {
        result += "\\X2\\";
        hasNonAscii = true;
      }
      // Encode as 4-hex UTF-16BE (BMP only; extend to \X4\ for surrogate pairs)
      result += code.toString(16).toUpperCase().padStart(4, "0");
    } else {
      if (hasNonAscii) {
        result += "\\X0\\";
        hasNonAscii = false;
      }
      result += char;
    }
  }
  if (hasNonAscii) result += "\\X0\\";
  return result;
}
// "콘크리트" → "\\X2\\CE58D06AC8B4B9AC\\X0\\"
```

## 8. Alternatives Considered

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| STEP serialization | Custom STEP text writer | `web-ifc` `SaveModel` | STEP grammar is complex; entity ordering, circular ref handling, schema validation all handled by WASM |
| Pset authoring | Hand-craft property map | Extend `revit-property-map.ts` as shared dictionary | Already has all thermal property names; bidirectional extension keeps read/write in sync |
| Worker communication | Custom serialization protocol | `Transferable` `ArrayBuffer` postMessage | Zero-copy transfer of Uint8Array; no JSON overhead |
| Korean string encoding | Use raw UTF-8 | `\X2\` STEP escape encoding | ISO 10303-21 compliance; maximum tool interoperability |
| IFC validation | Custom schema checker | buildingSMART validate.buildingsmart.org | Official, covers EXPRESS rules, mvdXML, bSDD |

## Open Questions

1. **G-SEED IFC Pset standard**
   - What we know: No standard IFC Pset for Korean 녹색건축 found in buildingSMART bSDD
   - What's unclear: Whether MOLIT or K-BIM Center has published an official IFC4 property set schema for G-SEED integration
   - Recommendation: Check `bim.go.kr` (Korea National BIM Center) and `gseed.or.kr` technical docs before Phase 43. If no standard exists, proceed with `KR_GreenBuilding_*` custom pset naming.

2. **COOP/COEP headers for SharedArrayBuffer (WASM MT mode)**
   - What we know: Multi-threaded WASM requires `Cross-Origin-Opener-Policy: same-origin` + `Cross-Origin-Embedder-Policy: require-corp`
   - What's unclear: Whether `next.config.ts` currently sets these headers; they may break third-party scripts
   - Recommendation: Default to single-threaded WASM in Phase 43. Add MT as a performance optimization in a follow-up PR only if 60s target is missed.

3. **ExpressID management at scale**
   - What we know: Each entity needs a unique expressID integer within the model
   - What's unclear: Whether web-ifc auto-assigns expressIDs when using `CreateIfcEntity`, or whether the caller must assign them
   - Recommendation: Check `GetMaxExpressID(modelID)` after each `WriteLine` call, or maintain a monotonically increasing counter starting at 1.

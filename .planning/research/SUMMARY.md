# Project Research Summary

**Project:** BIMFIT — Korean Building Energy Repository (v6.0)
**Domain:** Batch corpus generation, calibration statistics, and versioned dataset publishing, layered onto an existing Next.js/Vercel single-building BIM energy diagnosis app
**Researched:** 2026-09-15
**Confidence:** HIGH

## Executive Summary

This milestone turns a single-building energy diagnosis tool into a building energy repository: a versioned, citable corpus of Korean building baselines generated by sweeping the register through the app's own physics pipeline, anchored by measured reference models. Every new infrastructure need (batch generation, versioned releases, object storage, calibration) already has a proven-in-repo precedent to extend rather than invent. The recommended stack is small: GitHub Actions for the sweep, Vercel Blob for storage, simple-statistics for calibration math, hand-written JSON for metadata standards.

The single highest-leverage fix is not corpus-shaped: delivered-from-demand.ts hard-codes lighting at 15% and renewable at zero, blocking every LED/PV measure from moving the grade, and already feeds the seven published reference-building datasets. All research converges on fixing this before any corpus generation.

The dominant risk is epistemic, not technical: a named per-building assumption becomes an unnamed population bias at scale, and "the pipeline reproduces its own reference models' figures" must stay a permanently separate claim from "the corpus's error band reflects real Korean building performance" — the latter unsupportable from seven non-Korean, unmetered anchors.

## Key Findings

### Recommended Stack

Core additions: GitHub Actions scheduled workflow (sweep; chosen over Vercel Cron/Queues whose duration ceilings are too short for a quota-paced sweep), @vercel/blob@2.8.0 (release storage, zero new vendor account), simple-statistics@7.12.0 (CV(RMSE)/NMBE calibration math), reused zod@^4.3.6 and papaparse@^5.5.3, hand-written Table Schema JSON + schema.org/Dataset JSON-LD + CITATION.cff + GitHub-to-Zenodo DOI minting.

Do NOT use: tableschema/datapackage (dead 4-5 years), Parquet/DuckDB for v1 (repeats the superseded v7.0 Prediction plan's failed ordering), SQLite/Turso (corpus is immutable/publish-once, not mutable), Vercel Cron for the sweep, a new API framework, full DCAT or Croissant metadata.

### Expected Features

No prior-art system (DOE BPD, ASHRAE Building EQ, EU BSO, TABULA/EPISCOPE, ResStock/ComStock, CBECS/RECS, or any Korean source) combines bulk-downloadable per-record data, a public API, a stated modeled/metered distinction, and a calibration error band — that combination is BIMFIT's gap to fill.

Table stakes (P1): stable per-record identifier/permalink, provenance/licence/evidence-tier per record, schema documentation, bulk download, catalogue search/filter, and an explicit coverage/known-bias statement.

Differentiators (P2/P3): read-only paginated API, changelog/release versioning, peer-group percentile position with a transparent matrix, modeled/metered/assumption badge at corpus scale, calibration display with error band (gated on measured-consumption anchors), confidence tiering by anchor proximity.

Explicit non-goals: a single merged benchmark score (ENERGY STAR-style 1-100 — the EnergyStar++ critique shows the regression cannot capture nonlinearity and strata are often thin; show a band with stated N and a minimum-N suppression rule instead); and narrowing sweep coverage without stating it (Green Together and KEA both do this undisclosed — the fix is a stated boundary, not broader coverage). Also flagged: branding modeled output as "measured"; aggregate-only roll-ups replacing per-record data; merging as-designed and operational ratings into one number; treating a fixed archetype set as representing the current stock indefinitely.

### Architecture Approach

The interactive app and the new batch/corpus layer share one pure physics core (buildLedgerBaselineModel etc.); the batch job adds a second server-side entry point into that same pipeline rather than duplicating it. Storage extends the existing (currently orphaned) release-store.ts built for the superseded v7.0 plan, sharded by sigungu code so no API read loads the whole corpus into memory. A new pure benchmarks module computes peer-group percentiles once per release, shared by the corpus page, reference-model pages, and the twin — avoiding a fourth divergent computation path in a codebase that already has two disagreeing model registries and two disagreeing economics paths.

Major components: (1) src/app/api/corpus/generate/route.ts (new, reuses buildLedgerBaselineModel verbatim), (2) release-store.ts extended with a CorpusRow type, (3) src/lib/benchmarks/peer-groups.ts and percentiles.ts (new, pure), (4) delivered-from-demand.ts fixed in place with additive params, (5) a single converged retrofit-economics path (retrofit-bridge.ts calling into retrofit-delta.ts's method).

### Critical Pitfalls

1. A named assumption, scaled, becomes an unnamed population bias — publish assumption-prevalence tables per era/use bucket.
2. Calibrating against seven non-Korean, unmetered, synthetic anchors and calling it a Korean-stock error band — keep "pipeline consistency" and "population accuracy" as permanently separate claims.
3. Survivorship/coverage bias in the register, and the zero-vs-blank guarantee escaping its one enforcement point in new aggregation code — build all summaries on validated CanonicalEnergyModel objects, never raw JSON.
4. Non-like-for-like benchmark comparisons (thin peer groups, unnormalized climate, mismatched floor-area definitions, blended modeled/metered) — minimum-N floor, mandatory degree-day normalization, floor-area-definition tagging.
5. Publishing traps: immutability, schema drift, licence contamination, and PII reachable at bulk scale — append-only versioning, additive-only schema evolution, licence-lineage tracking, a privacy/redaction gate as go/no-go before publish.
6. Physics-ratio replacement breaking around 380 dependent tests quietly — re-triage by assertion intent, version-stamp batches, never merge pre/post-fix corpus generations into one release.

## Implications for Roadmap

ARCHITECTURE.md and PITFALLS.md agree on overall sequencing but frame the feasibility-research gate differently: ARCHITECTURE.md allows the corpus-generation route to be built and tested small in parallel with feasibility research, while PITFALLS.md (and PROJECT.md's own Key Decisions) treat feasibility research as a hard gate before any phase commits to scale. This synthesis adopts the stricter PITFALLS.md reading — a route/script skeleton may be built and tested on a handful of buildings in parallel, but no full-scale sweep is scoped until the pilot's quota and field-completeness findings are in — because the downside of guessing wrong (a poisoned shared API key, a silently-truncated "nationwide" coverage claim) is asymmetric and hard to walk back once published.

### Phase 1: Fix delivered-from-demand.ts (the physics gate)

Rationale: every other honest number in this milestone sits on top of this function. No dependency on anything else; unanimous across all research.
Delivers: additive lightingDemandKwh/renewableGenerationKwh fields reusing existing correct lighting/PV computations; a named operatingHours assumption; a DeliveredEnergyProvenance type.
Avoids: Pitfall 7 — exit criteria require the ~380-test suite re-triaged by intent, a measured before/after delta, and a version marker.

### Phase 2: Reconcile the two retrofit-economics input paths

Rationale: depends on Phase 1; independent of Phase 3.
Delivers: analyzeRetrofitEconomics calls computeRetrofitDelta instead of hand-rolling its own formulas.
Avoids: a third economics computation path (named anti-pattern in ARCHITECTURE.md).

### Phase 3: Collapse the two model registries (parallel-eligible)

Rationale: independent of all other phases; sequence before corpus-sourced buildings need gallery representation.
Delivers: REFERENCE_BUILDING_IDS as the single registry; GalleryItem becomes a thin editorial overlay generated from the manifest.

### Phase 4: Register sweep feasibility research (pilot, gates scale)

Rationale: must answer both quota and field-completeness-at-scale (blank-date rates, endpoint-partial-success) before Phase 5 is scoped.
Delivers: a scoped, checkpointed pilot sweep's measured findings.
Avoids: Pitfall 6 (silent partial-sweep truncation) and Pitfall 3 (register survivorship bias).

### Phase 5: Corpus generation at scale

Rationale: depends on Phase 1 and Phase 4's findings; must never share request budget/API key with the interactive lookup.
Delivers: the generation route + driver script, checkpointed/resumable; per-row provenance fields; assumption-prevalence tables; an exclusions log instead of filled-in guesses.
Avoids: Pitfalls 1 and 3.

### Phase 6: Storage, versioned release publishing, and read-only API

Rationale: depends on Phase 5 producing real rows to validate storage design against.
Delivers: sharded release storage, a CorpusRow schema, append-only versioning, corpus API routes, a /corpus browse page, and a privacy/redaction pass plus licence-lineage audit as explicit go/no-go exit criteria.
Avoids: Pitfall 5 in full.

### Phase 7: Grow the anchor set with measured-consumption, Korean, typology-gap buildings

Rationale: prerequisite for real calibration — today's anchors have measured envelopes, not measured consumption, and none are Korean.
Delivers: additional anchors with real metered data.

### Phase 8: Calibrate corpus baselines against measured anchors; replace the retrofit panel

Rationale: last tier by design — depends on Phase 6 (a real corpus) and Phase 7 (measured anchors).
Delivers: peer-group percentile/benchmark module with a minimum-N floor; methodology text keeping "pipeline consistency" and "measured accuracy" claims separate; the retrofit panel replaced with energy/carbon/corpus-position, priced off Phase 2's real modeled savings.
Avoids: Pitfalls 2 and 4.

### Phase Ordering Rationale

- Physics before everything: unanimous.
- Registry collapse is parallel-track, not blocking.
- Feasibility research gates scale, not existence (stricter PITFALLS.md reading adopted deliberately given asymmetric downside).
- Storage follows generation, not the reverse — validate design against real row volume.
- Anchor growth and calibration are last by construction: calibrating without measured anchors is Pitfall 2's exact failure; benchmarking without a real corpus is statistically meaningless.

### Research Flags

Needs research: Phase 4 (sweep feasibility, is itself a research phase), Phase 8 (confirm exact ASHRAE Guideline 14 thresholds against a licensed copy; methodology text needs standalone review against Pitfall 2), Phase 6 (privacy/redaction gate has no existing precedent in this codebase).
Standard patterns (skip research-phase): Phase 1 (already scoped to file:line), Phase 3 (fully scoped in ARCHITECTURE.md Q4), Phases 5/6 (extend proven-in-repo precedents).

### Gaps to Address

- Register sweep quota and field-completeness at scale: unmeasured — handled via Phase 4's mandatory pilot.
- Whether a separate data.go.kr credential is obtainable (vs. sharing the rate-limited demo key): unresolved in all four files; raise explicitly during Phase 4; if unavailable, the sweep must yield to interactive traffic rather than compete with it.
- Licence model for register-derived records: differs from the curated reference-model rights profile (some of which are academic/research-licensed BIM test files). Unresolved — needs a named legal/licence review gating Phase 6's publish, not an assumption carried over from reference-model licensing.
- Minimum peer-group cell size before a percentile may be stated: no number fixed by research. CBECS's suppress-if-RSE-over-50-percent-or-n-under-20 rule is the closest analogue, but Phase 8 must set and justify a project-specific threshold rather than assume it transfers directly.
- Whether Korean metered sources (Green Together / KEPCO) would licence data for calibration: not established; Phase 7 treats this as an open acquisition question. If it resolves negatively, Phase 8's calibration claim stays scoped to "pipeline consistency only" indefinitely.
- The seven existing anchors' evidentiary limit, stated plainly: they can support a claim that the pipeline reproduces its own reference models' figures consistently (internal consistency, verifiable today) but CANNOT support a stated error band for the Korean building stock (population accuracy) — non-Korean, unmetered, synthetic anchors, model-vs-model not model-vs-reality. These two claims must stay textually separate everywhere they surface, and Phase 8's exit criteria should include an explicit check that no surface conflates them.
